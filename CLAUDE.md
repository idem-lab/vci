## Project overview

<!-- REPLACE: one paragraph on what this package does and, more importantly,
WHY the core design decisions were made. Claude can read the code for structure
but cannot infer intent. -->

`vci` is an R package that implements the Vector Atlas 'Vector Control Impact'
spatial modelling framework. See DESIGN.md for the original design spec.

This is a public repository maintained by two people. All work is done with
local Claude Code agents; there is no `@claude` GitHub Actions automation.

## Package layout

Standard R package structure. Notably:
- `R/` — package source. One topic per file where practical.
- `tests/testthat/` — tests (testthat 3rd edition).
- `vignettes/` — long-form usage; a first-class deliverable, not an afterthought.
- `man/` — generated by roxygen2. **Never edit by hand.**
- `dev/sessions/` — auto-generated Claude session logs (see Transparency). Listed
  in `.Rbuildignore` so it does not affect `R CMD check`.

## Development workflow: test-driven

We work test-first. For any behaviour change:
1. Write or update a failing `testthat` test that captures the intended behaviour.
2. Implement the minimum to make it pass.
3. Refactor with the test green.

Do not add code paths that aren't covered by a test. If a bug is fixed, a
regression test that would have caught it is part of the fix.

## Documentation is a first-class deliverable

Documentation is not a trailing chore — it ships with the change:
- **roxygen2** (Markdown syntax) for all exported functions. Run
  `devtools::document()` after changing any roxygen block; never edit `man/`.
- **Examples**: every exported function has runnable `@examples` that are
  practical and coherent — they should demonstrate real use, run cleanly under
  `R CMD check`, and read as something a user would actually write. Prefer a
  small, meaningful example over a contrived one. Use `\donttest{}` /
  `\dontrun{}` only when genuinely necessary, and say why.
- **Vignettes**: when a change affects how the package is used, update the
  relevant vignette in the same PR. A user-facing feature without a vignette
  update is incomplete.
- **NEWS.md**: add a bullet under the top header for any user-facing change,
  following the tidyverse NEWS style.

## Dependency policy (important — read before adding any dependency)

We minimise dependencies and strongly prefer well-used, stable ones:
- Do **not** add a dependency for something a few lines of base R can do.
- Before adding a package, weigh it: how widely used and actively maintained is
  it? A niche or single-maintainer package is a liability even if convenient.
- **Prefer matching a stable dependency's design over adding a new one.** If
  adapting our own code/style to how a well-established package is designed
  avoids a new dependency (or an unstable one), do that — even if it means
  writing it differently than we first intended. Idiomatic use of a solid
  dependency beats a bespoke abstraction over a shaky one.
- If you believe a new dependency is warranted, do not just add it — flag it in
  the PR with the reasoning so a human decides.
- Use `Imports:` for runtime deps, `Suggests:` for things used only in tests,
  vignettes, or examples. Add via `usethis::use_package()`.

## Code style & linting

- Follow the **tidyverse style guide** (https://style.tidyverse.org).
- Formatting and linting are enforced by tooling, not by Claude reasoning about
  style: run the formatter (Air, or `styler::style_pkg()`) and
  `lintr::lint_package()` before finishing. Fix lints rather than suppressing
  them; if a suppression is truly needed, comment why.
- Do not restyle code unrelated to the current change — keep diffs focused.

## Definition of done (run before opening a PR)

A task is done only when all of these pass locally:
1. `devtools::document()` — docs regenerated, `man/` up to date.
2. `devtools::test()` — all tests pass, new behaviour covered.
3. Formatter + `lintr::lint_package()` — clean.
4. `devtools::check()` — **0 errors, 0 warnings, 0 notes.** Treat any NOTE as
   something to resolve or explicitly justify in the PR.
5. Vignettes and NEWS.md updated if the change is user-facing.

Do not open a PR with a failing check. If you cannot get to a clean check,
stop and surface the blocker rather than papering over it.

## Branch & PR conventions

We use the `usethis` pull-request flow:
- Start work with `usethis::pr_init("branch-name")` — always a feature branch,
  never commit to `main`.
- Branch names: short, hyphenated, descriptive, prefixed with the issue where
  useful, e.g. `iss42-parser-edge-cases`.
- Push / open the PR with `usethis::pr_push()`. **Open as a draft** while work
  is in progress so CI runs without notifying reviewers; mark ready when done.
- The PR body must contain `Fixes #<issue-number>` (or `Refs #<n>` if partial).
- One logical change per PR. Keep them reviewable.
- **Commit the session log before marking the PR ready.** `dev/sessions/<file>.md`
  is rewritten by the Stop hook at the end of every turn, but is never staged for
  you. An uncommitted log means the prompts behind the change never reach the
  reviewer, which defeats the point. CI fails the PR if it is missing.

## Collaboration (two maintainers)

- Only work an issue that is **assigned to you**. If an issue is unassigned,
  assign it before starting so we don't both point agents at the same one.
- Never push directly to `main`; everything lands via reviewed PR.
- Neither of us merges our own agent's PR blind — a human reviews every PR,
  including each other's Claude-generated ones.

## PR description: "How this was produced" (transparency)

Because work is done by local agents, every PR you open must include a short
section in the description so a reviewer sees the reasoning, not just the diff:

```
## How this was produced
- Issue: #<n>
- Core prompt(s): <the essential instruction(s) you gave>
- Key decisions / trade-offs Claude made or asked about: <bullet(s)>
- New dependencies (if any) and why: <or "none">
- Session log: dev/sessions/<file>.md
```

Populate this from the actual session. The full prompt-by-prompt record is
captured automatically in `dev/sessions/` (see below); this section is the
executive summary.

## Flag AI-authored GitHub content as Claude

Agents act with a maintainer's GitHub credentials, so anything you post — issues,
PR descriptions, comments — appears under a human's identity by default. On a
project whose point is to make the AI role transparent, that is the wrong default:
a reader cannot tell your text from the human's, and the two sit in the same
threads.

So prefix every issue, PR description, or comment you author with this notice as
its first line (substitute the account you are posting from):

```
> 🤖 **Posted by Claude (Opus 4.8)**, an AI coding agent, from the **@<account>** account — not written by a human.
```

- This applies to text an agent authors, never to text a human types. Do not
  annotate a maintainer's own comments.
- It covers GitHub-native surfaces only. Commits are attributed through the
  `Co-Authored-By: Claude` trailer instead (see Branch & PR conventions), not by
  editing file contents.
